# 개발용 실제 Linux 환경 자원 점검

## 2026-09-17: Android·Conda 검증 시 발열 제한

Android 에뮬레이터 안의 ARM guest와 별도 x86 Conda VM을 동시에 검사하다 CPU88°C를 확인했다. 소유 Conda 검사기를 SIGINT로 중단하고 finally에서 해당VM이 종료된 것을 확인했다. 검사중간 결과를 전체통과로 저장하지 않았으며 작업overlay와 기존배포팩은 보존했다. 이후 무거운VM 검사는 직렬 실행한다.

Gradle 재빌드에는 해당 작업만의 `systemd-run --user --scope -p CPUQuota=100%`와 `--max-workers=1`,nice15를 적용했다. 이 상한은 전체코어합계로CPU1개 분량이며 스레드를특정코어에고정하는것이아니다. 다른 앱과 사용자VM의 설정을 바꾸지 않았다. 낮은 우선순위만으로 CPU상한이나 온도제한을 보장하지 않으므로 센서를 별도로 확인한다. APK계측시 에뮬레이터 부팅 구간의온도는80°C대로 오를수있었으며 이를휴대폰발열측정결과로일반화하지않는다.

ARM Conda 빌더도 처음100%상한으로실행했으나13분이후CPU82°C를확인해해당scope만65%로낮췄다. 전체시스템의CPU정책을바꾸거나다른VM을중단하지않았다. 이수치는개발검사의부하제한이며앱배포성능설정으로고정하지않는다.

Android 소프트웨어 렌더링 에뮬레이터에는 지나친 CPU 제한도 문제가 됐다. 65%로 부팅한 전용 AVD에서 시스템 UI 응답 없음 창이 입력을 가로챘다. 이를 앱 키보드 결함으로 처리하지 않고, 전용 AVD만 정상 종료 후2vCPU/합계150%상한으로 재시작했다. 렌더 픽셀을720×1280/density280으로 줄여 같은 논리 화면 크기를 유지했다. 정상 부팅27초, 정규검사25개 중22실행 통과/3선택 제외94.26초. 그때의 센서 관측은 약50°C, 실제 게스트 부팅 관측은65°C였다. 실휴대폰 성능 측정은 아니다.

큰 이미지의 불필요한 반복 처리도 줄였다. `stageLinuxPack`의 네 원본 파일·스테이징 스크립트·생성물 의존성을 선언하고, 두 번째 실행의 `UP-TO-DATE`를 확인했다. 입력 변경 시 SHA 검증과 조각 생성은 그대로 실행하며, 변경 없는 Java/UI 재빌드에서1.7GB를 다시 읽고 나누지 않는다.

## 지속 CPU 사용 원인과 수정

- 이미지 빌더가 가속 장치를 보지 못한 제한된 검사 결과에 따라 TCG 에뮬레이션을 사용했다. 실제 개발 호스트에서는 KVM을 사용할 수 있었다.
- 게스트 제어 채널에서 연결이 끊기면 `readline()`이 즉시 빈 결과를 반환했다. 곧바로 다시 읽는 반복문이 한 가상 CPU를 계속 소모했다.
- KVM 사용 가능 여부를 실제 장치 열기/API 조회로 검사한다. 일반 앱은 가속 실패 시 TCG로 자동 대체하지 않는다. Windows는 WHPX 초기화 실패를 그대로 보고하며 소프트웨어 대체를 하지 않는다. Windows 실기기 검증은 아직 남아 있다.
- 빈 읽기 뒤 250ms 대기하며 재연결을 수용한다. 단순 `select()`만 추가하면 연결 종료 상태에서도 즉시 반환할 수 있어 이 버그가 해결되지 않는다.
- 가상 CPU는 가용 CPU의 절반, 최소 1개/최대 4개를 기본 배정한다. 2/4/6/8개인 PC에서는 각각 1/2/3/4개이다. 이는 호스트 CPU 사용량 상한이나 발열 제한이 아니다.
- 호스트 응답성을 위해 QEMU의 스케줄링 우선순위를 낮춘다. 사용하지 않는 개발 VM은 종료한다. TCG는 개발자가 명시적으로 `--allow-software`를 지정할 때만 허용한다.

## 실측

호스트: Intel Core Ultra 7 258V, 8코어. QEMU 8.2.2, Ubuntu 22.04 게스트, 2 GiB RAM.

| 조건 | 구간 | QEMU CPU: 한 논리 CPU = 100% | 호스트 8개 CPU 합계 대비 |
| --- | --- | --- | --- |
| KVM, 제어 채널 반복문 수정 전, 연결 없음 | 8초 | 98.50% | 12.31% |
| KVM, 반복문 수정 후, 연결 없음 | 10초 | 1.10% | 0.14% |
| KVM, 확장 과제 검증 후 다시 측정, 연결 없음 | 5초 | 0.80% | 0.10% |

`/proc/<확인된 QEMU PID>/stat`의 사용자/커널 CPU 시간 차이를 벽시계 구간으로 나눈 측정이다. `ps %CPU`의 프로세스 수명 평균과 혼동하지 않는다. 위 수치는 대기 상태의 짧은 측정이며 부팅, 패키지 설치, ROS 통신, 빌드 중 사용량이나 모든 PC의 성능을 보장하지 않는다. 온도/전력 저하를 직접 측정한 결과도 아니다.

회귀 검증: `test_guest_idle.py`는 연결 종료 후 대기와 재연결 처리를, `test_vm_resources.py`는 코어 배정/가속 실패 시 자동 에뮬레이션 방지를 검사한다. 실제 VM 검증은 명시적으로 실행하는 `test_live_guest.py`로 nano 저장/종료/채점과 터미널 간 파일 공유/환경 분리를 확인한다.

추가 측정은 개발 VM PID와 명령행을 확인한 뒤 `/proc/<pid>/task/*/stat`의 각 스레드 CPU 시간을 5초간 비교했다. 스레드 합계 0.8%였으며, VM은 4 vCPU와 nice 10으로 실행 중이었다. 마지막 ROS 회귀 검사 두 개를 통과한 뒤 개발 VM을 정상 종료했다. CPU 개수를 늘려 무한 반복을 감추는 방식이 아니며, 낮은 우선순위도 발열 상한을 보장하지 않는다.

## 런타임 팩 직접 실행 검증

동일 호스트에서 앱 엔진이 3,617,980,416바이트의 독립 qcow2 기반 이미지를 읽기 전용으로 사용하고, 임시 overlay를 생성해 `-nic none`으로 실행했다. Docker 설치는 게스트 안에 있으며 호스트 Docker 소켓은 연결하지 않았다.

- 제어 채널과 준비 마커 확인: 1.58초. 이는 ROS 노드 준비/수업 표시까지 포함한 총 UI 시작 시간과 다르다.
- 실제 ROS 파라미터 변경, 미완료→완료 채점, 실제 게스트 PNG 화면 수신까지 포함한 전체 테스트: 10.96초.
- VM 종료와 임시 디스크 삭제: 0.07초. 기반 이미지 크기/수정 시간이 변하지 않는 것도 확인했다.
- 실제 ROS 추가 테스트 12개에서 20개 단원의 기본 동작을 검사했다. 모든 활용 변형·종합 복습의 검증을 의미하지 않는다.
- 네이티브 종료 회귀 테스트 6개에는 준비 작업 중 취소와 중복 종료 방지가 포함된다. 당시 미완료였던 Linux 앱 비정상 종료 정리는 아래 4.1.2-dev에서 추가 검증했다. Windows 실기기 검증은 남아 있다.

ROS 교육 명령은 설치된 Humble 도구와 [공식 다중 노드 실행 문서](https://docs.ros.org/en/humble/Tutorials/Beginner-CLI-Tools/Launching-Multiple-Nodes/Launching-Multiple-Nodes.html)를 대조했다. GUI는 별도 모방 그림이 아니라 게스트 Xvfb의 실제 TurtleSim 화면을 읽는다.

### 4.1.1-dev 팩 재검증

로컬 APT·Docker 레지스트리가 포함된 새 기반 이미지는 4,111,794,176바이트이다. 패키징된 실행 파일의 `--self-test-real`에서 실제 ROS/게스트 화면/APT 설치/Docker 갱신/save·load가 네트워크 장치 없이 통과했다. 제어 채널 준비 1.55초, 종료 0.04초이며 최종 확인 시 개발·검증 QEMU 프로세스는 남아 있지 않았다. 낮은 우선순위 빌드 직후 호스트 `x86_pkg_temp` 값은 45,000 m°C였다. 한 시점의 센서 값이며 최고 온도나 열 스로틀링 여부를 검증한 것은 아니다.

### 4.1.2-dev 비정상 종료 뒤 자원 해제

앱이 정상 종료 처리를 수행하지 못해도 전용 관리 프로세스가 파이프 종료를 감지해 자신이 만든 VM을 정리한다. 관리 프로세스는 입력이 없을 때 블로킹 읽기와 250ms 이벤트 대기를 사용한다. 기록된 PID에 신호를 보내는 일괄 청소는 하지 않는다.

Linux 실행 파일에서 시작 도중·준비 완료 후 앱의 비정상 종료를 각각 검사했고, VM·관리 프로세스·임시 실습 디스크가 남지 않았다. 실제 QEMU의 관리 프로세스까지 강제로 종료한 별도 검사에서도 QEMU가 종료됐으며 잠금이 풀린 전용 디스크를 회수했다. 준비 전 앱 종료, 살아 있는 다른 인스턴스, 알 수 없는 파일과 링크 보존도 회귀 검사에 포함한다. 기반 이미지와 진도는 정리 대상이 아니다.

최종 실행 파일의 실제 ROS/APT/Docker 검사도 통과했다. 제어 채널 준비는 2.43초, 정상 종료는 0.11초였으며 최종 확인 시 검증 VM·관리 프로세스가 남아 있지 않았다. 독립 관리 프로세스 추가 전후의 CPU/메모리를 동일 조건에서 비교한 수치는 아직 없으며 Windows 동작을 검증한 결과도 아니다.
