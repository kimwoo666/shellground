## 1. 결론과 증거의 범위

큰 NumPy·Matplotlib·pandas 범위를 새로 만들 필요는 없다. 현재의 주된 실습 공백은 **실제 노트북에서 커널을 선택·등록하고, 재시작 뒤 문서를 재실행하며, 터미널과 노트북의 Python 불일치를 해결하는 행동**이다. `py_kernel`은 재대입과 이전 계산값을 실제 Python에서 연습하지만 이 행동들을 대신하지 않는다.

`quiz_practice_links.json`의 **exact 0 / related_practice 55 / unmapped 5**는 원래 후속 과제와의 엄격한 일치 여부다. **55개 역량이 미구현됐다는 뜻이 아니다.** 데이터·출력 이름·문제 조합이 달라도 같은 역량을 연습하는 항목이 많다. 원 후속 과제의 완료와 관련 연습의 완료를 구분하는 `completion_equivalence=false`는 그대로 유지해야 한다.

이번에는 다섯 PDF 원문을 열거나 다시 추출하지 않았다. PDF 범위·물리 페이지 판단은 기존 `quiz_blueprint.md:101`의 범위표와 `:401` 이후의 원문 대조 기록을 근거로 한다. 그 기록을 재확인했다는 뜻이지, 이번에 원문을 직접 검증했다는 뜻은 아니다. `PYTHON_EXPANSION.md`의 실행 통과 기록도 과거 보고로만 읽었으며 재실행하지 않았다.

읽은 대상은 `quiz_blueprint.md`, 33개 `concept_cards.json`, 60개 `quiz_bank.json`의 문항·해설·후속 목표, `course.py`의 조합 구조, `library_course.py`, `review_course.py`, 60개 `quiz_practice_links.json`, `PYTHON_EXPANSION.md`다. 근거를 좁히기 위해 등록된 기초·NumPy·pandas·그림·통합·시간 측정 단원 선언도 읽었다. 파일 읽기와 JSON/AST 정적 검사만 했으며 과정/채점 모듈 import, 학습 코드 실행, VM·설치·빌드는 하지 않았다.

현재 연결 데이터가 기록한 Python 91단원/273문제는 `course.py:6`의 기존 과정 + 통합 삽입 + 13복습 + 6개 라이브러리 보충이라는 구조와 일치한다. 아래 `예시/활용1/활용2`는 각각 문제 인덱스 `0/1/2`다. 파일·행은 감사 당시 소스 위치다.

### B. 숫자가 아닌 실제 차이: 좁게 설명하고 보완 여부를 정한다

- `notebook-execution-order`, `install-versus-import`: 실제 커널 조작과 환경 비교라는 행동이 다르다. 이번 Jupyter 구현의 우선 대상이다.
- `pandas-concat-labels`: 원 라벨 유지와 새 숫자 라벨은 반대 정책이다. 단순 예제 치환이 아니다.
- `pandas-weather-missing-group`: mean의 분모·유효 count·월/연도의 결합 판단이다. 기존 합계 예제만으로 동일 완료라고 할 수 없다.
- `plot-heatmap-colorbar`: 실제 colorbar는 있지만 지정 색 범위와 단위 라벨은 현재 연결 목표에 없다. **원 후속 과제의 추가 조건**이며 현재 PDF 분석만으로 vmin/vmax/label 호출을 반드시 강의 필수 API라고 단정하지 않는다.
- `python-function-loop`: 함수/반복/return은 배웠지만 ‘빈 목록도 처리하는 누적합 함수’의 전용 새 입력 검사는 다르다. 이를 함수 개념 전체 누락으로 부풀리지 않는다.
- `plot-axis-scale-interpretation`, `plot-chart-question`, `plot-scatter-meaning`: 관련 그래프를 그리는 것과 이유·인과 한계를 직접 말하는 것은 다른 평가다. 현재 개념 퀴즈는 핵심 오해를 이미 확인한다. 더 깊은 서술 평가를 원할 때만 별도 목표를 둔다.
- `pandas-csv-index`: 파일과 StringIO의 차이는 입력 매체 차이이며 CSV/index_col 역량은 같다. 실제 파일 입력은 이미 있으므로 StringIO 미사용을 핵심 환경 준비 공백으로 분류하지 않는다.

unmapped5개는 `cloud-session-storage`, `data-science-small-sample`, `bigdata-three-vs`, `data-versus-information`, `science-four-paradigms`다. 모두 대응 개념 카드/선택 퀴즈는 있다. 원본 복구 계획·분석 질문·사례 분류의 **자유 과제용 실행 채점기**가 없다는 뜻이다. 3V나 패러다임을 위해 불필요한 Python 코드를 작성시키지 않는다.

`quiz_blueprint.md`의 L0–L8 및 R5는 설계 기록이며 등록 단원이 아니다. R5의 전 강의 CSV→결측 정책→배열/피벗/결합→그림→해석 과제와 현재13개의 ‘직전5단원 복습’은 다르다. 현재 복습이 없다는 주장은 틀리지만 전체 파이프라인 숙달을 모두 확인했다는 주장도 피한다. 이를 닫는다면 먼저 작은 날씨 결합 과제로 시작하고 별도의 대형 과정 재설계로 확대하지 않는다.

## 4. 실제 Jupyter 단원 설계 공통 계약

아래는 **새 설계안**이다. 제안 key는 아직 등록된 실습 key가 아니며 연결 JSON이나 완료 진도를 변경하지 않았다. 기존 기반 과정 뒤의 독립 ‘실제 노트북’ 묶음으로 두고 `py_kernel`, `py_import`, NumPy 기초를 선수로 삼는다. 마지막 단원은 기존 Conda 환경 선택·`pip_install`을 선수로 추가한다. 등록 단원 직전에 Conda의 활성화/인터프리터 확인을 짧게 연결한다.

부모가 공유한 구현 방향은 네이티브 Python 화면 안의 코드/Markdown 셀 + 실제 Linux VM + 공식 ipykernel/jupyter_client다. 웹 브라우저나 Jupyter 서버가 별도로 있어야 한다고 가르치지 않는다. 아래는 그 계약을 기준으로 한 제안이며 실행 검증 결과가 아니다.

### 준비되는 두 환경과 표시

| 화면 설명 | 실제 준비 조건 | 학습자에게 미리 알려 줄 정보 |
|---|---|---|
| 기초 Python | 앱 전용 Conda 환경 A, CPython3.12 계열, 실제 ipykernel/pip, NumPy 없음 | 환경 이름, Python 전체 경로, 준비된 패키지 차이 |
| 분석 Python | 다른 prefix의 환경 B, 같은 Python3.12 계열, 실제 ipykernel/pip, 공식 NumPy2.3.5 | 이름이 아니라 실제 경로로 두 환경을 구분할 수 있음 |

구현할 때 A/B를 실제 이름·경로로 치환해 화면에 제공한다. 둘의 **Python 버전 문자열이 같아도 서로 다른 환경**임을 이용한다. 학습자가 경로를 추측하거나 관리용 base를 선택하게 하지 않는다. 보호 base·관리 통신 환경은 학생 과제가 아닌 내부 보존 조건이다. 환경/공식 자산 준비 실패는 학습자 오답이 아니라 ‘준비 실패’로 분리한다.

기초 환경에 NumPy를 설치하는 마지막 활용 문제는 문제 전용 두 환경으로 시작한다. 다른 문제의 초기 부재 조건을 망가뜨리지 않도록 실습 초기화 경계를 명시하고, 재채점 때는 같은 셀·같은 환경을 보존한다. 초기화는 학습자에게 알리고 명시적으로 수행한다.

### 무엇을 실제로 채점하는가

1. 실제 kernelspec의 시작 프로그램과 실제 커널 프로세스의 prefix/실행파일, 그 커널에 보낸 코드의 결과를 함께 본다. 화면의 display_name, 노트북 metadata, 출력된 경로 문자열만으로 환경을 인정하지 않는다. 경로 비교는 정규화하고 정확한 Python patch 버전은 요구하지 않는다.
2. 셀의 출력은 해당 실제 실행 요청의 응답에 연결한다. 예전 노트북 출력이나 다른 커널의 늦은 응답을 현재 결과로 쓰지 않는다. 진단은 학습자 변수명을 덮어쓰지 않고 실행 번호의 연속성 자체를 점수로 삼지 않는다.
3. 재시작 목표는 앱이 관리하는 실제 커널 프로세스/프로토콜 세대 변화와 새 상태를 확인한다. `del`/변수 지우기만으로 재시작했다고 인정하지 않는다. 반대로 동일한 환경의 실제 종료→새 시작도 같은 결과라면 허용한다. 특정 버튼 문자열이나 CLI 입력 이력을 요구하지 않는다.
4. 재현 목표는 새 실제 커널에서 현재 문서의 코드 셀을 위에서 아래로 실행하여 오류 없이 목표값이 나오는지 확인한다. 숨은 준비 변수는 없어야 한다. 검증이 별도 커널을 사용한다면 학생의 현재 커널을 몰래 갈아끼우지 않고 검증 목적·진행을 표시한다.
5. 오류 관찰 단계의 `NameError`/`ModuleNotFoundError`는 **의도된 중간 결과**다. 초기 오류가 있었다는 이유로 나중의 수정 풀이를 거부하지 않는다. 최종 계산의 오류와 분리한다. 설치 문제는 실제 패키지 상태+새 커널 import로 확인한다.
6. 결과 조건은 목표에 쓴 변수·문서·환경만 검사한다. 별칭, 중간 변수, 코드 줄 수, 파일의 JSON 들여쓰기, 실행 번호가 특정 수인지 등을 숨은 정답으로 삼지 않는다. 출력만 하도록 한 문제와 변수 결과를 남기는 문제의 목표도 명확히 구분한다.

이 기준의 기술 근거: 커널은 UI와 분리된 실제 프로세스다([Jupyter kernels](https://docs.jupyter.org/en/latest/projects/kernels.html)). kernelspec에는 실행 argv와 화면 이름이 분리돼 있다([Jupyter Client kernelspec](https://jupyter-client.readthedocs.io/en/stable/kernels.html#kernel-specs)). 메시지의 parent_header는 실행 요청과 결과를 연결하며 재시작 때 커널 session 식별자가 바뀐다([Jupyter messaging](https://jupyter-client.readthedocs.io/en/stable/messaging.html#general-message-format)). 이 문서는 이를 이용한 **제안 채점 계약**이지 새 실행 엔진 구현이 아니다.

## 5. 짧은 단원5개 · 예시/활용 총15문제

### J1 `jupyter_select`: 문서와 실행할 Python을 구분하기

새 개념은 **커널 선택이 이 문서를 실행할 Python을 정한다**는 것이다. 등록은 아직 시키지 않는다. `sys.executable`은 실행파일, `sys.prefix`는 해당 환경의 위치라고 먼저 설명한다. 앱 자체의 Python과 VM의 학습 Python은 별개다.

소단계:

1. Markdown 설명 셀과 코드 셀을 구분한다. 설명 셀은 Python으로 실행하지 않는다.
2. 준비된 진단 코드 `import sys; print(sys.executable); print(sys.prefix)`를 코드 셀에서 실행하고 제공된 환경 표와 비교한다.
3. 커널 목록에서 목표 환경을 선택하고 같은 진단을 다시 실행한다. 이 앱은 전환 시 새 커널을 시작하므로 코드 셀은 남지만 이전 변수는 가져오지 않는다. 일반 Jupyter에서 다른 기존 커널에 재연결하는 동작까지 항상 새 상태라고 일반화하지 않는다.

- **예시 — 분석 환경으로 바꾸기:** 기초 커널 선택 상태, 진단 셀과 `import numpy as np; total=np.array([2,5]).sum()` 셀이 준비됨. 분석 커널로 바꾸고 total을 계산한다. 통과: 실제 B prefix/NumPy 경로, total=7. 오답: A에서 NumPy를 새로 설치해 같은 값만 만들기, 화면 이름만 바꾸기. 동등: 허용된 다른 표시 이름의 실제 B 커널 선택.
- **활용1 — 설치 없이 기초 환경 사용하기:** 분석 커널에서 시작. NumPy를 쓰지 않는 `width=6; height=4; area=width*height` 문서다. 기초 커널을 선택하고 area를 계산한다. 통과: 실제 A, area=24, 목표에 명시한 두 환경의 패키지 구성 유지. 오답: 계산은 맞지만 B인 상태. 목적은 불필요한 설치가 아니라 적절한 실행 환경 선택이다.
- **활용2 — 같은 버전의 두 Python 구별하기:** 두 커널 모두 같은3.12 버전, 표시 이름에도 버전만 보이지만 제공된 상세 정보에 경로가 있음. 지정된 분석 환경에서 `values=[3,7]; result=sum(values)`를 실행한다. 실제 B에서 result=10이면 통과. 버전 출력만 같다고 A를 선택하면 거부한다. 화면 이름을 외우는 검사는 하지 않는다.

연결: `install-versus-import`, `conda-project-isolation`, 카드 `python-selected-environment`. 예시와 활용1/2는 각각 라이브러리 필요에 따른 선택, 불필요한 설치 회피, 동일 버전 환경 구분이다.

### J2 `jupyter_order`: 셀을 편집한 것과 실행한 것을 구분하기

새 개념은 **현재 값은 마지막으로 실행한 순서의 결과**라는 것이다. 재시작은 다음 단원에서 배운다. 문서 위치 번호와 실행 번호는 다른 것이며 숫자가 연속이어야 정답인 것은 아니다.

소단계:

1. 정의 셀을 실행한 뒤 이를 사용하는 계산 셀을 실행한다.
2. 정의 셀을 편집만 하고 값을 관찰한다. 편집은 아직 실행이 아니다.
3. 정의 셀만 실행해도 이미 계산된 total은 그대로임을 관찰하고 계산 셀까지 다시 실행한다.
4. 셀을 다시 실행하면 목록 변경 같은 동작도 반복됨을 작은 append 예제로 설명한다.

- **예시 — 과거 계산값 재계산:** C1 `price=8`, C2 `total=price*3`를 실행한 상태. C1을10으로 바꾸고 실행한 뒤 total이24인 중간 상태를 확인하고 C2를 다시 실행해30을 만든다. 단계별 실제 값으로 확인한다. total만30으로 직접 쓰고 가격은8인 상태는 거부. 관찰 답에는 ‘편집/원인 셀 실행/의존 셀 실행’ 중 어느 행동이 total을 바꾸는지도 확인한다.
- **활용1 — 정의보다 사용이 먼저인 문서 고치기:** 새 커널, 위 셀 `subtotal=unit_price*quantity`, 아래 셀 `unit_price=7; quantity=4`. 위를 먼저 실행하면 NameError가 남는다. 정의 셀을 위로 옮기거나 위쪽 코드에 필요한 정의를 추가하고 위에서 아래로 실행해28을 만든다. 둘 다 허용. 의존 순서를 바로잡지 않고 현재 커널에만 이름을 만들어 실행하는 것은 문서 순서 검증에서 거부한다.
- **활용2 — 다시 실행할 때 중복 추가됨을 고치기:** C1 `items=[2,5]`, C2 `items.append(7); total=sum(items)`이고 C2를 두 번 실행해 목록에7이 두 번 들어간 상태. ‘C2를 여러 번 실행해도 원래 items=[2,5]를 유지하며 result=[2,5,7], total=14’라는 목표로 고친다. `result=items+[7]` 등 새 결과를 만드는 동등 풀이 허용. items의 현재 상태도 복구해야 한다는 목표를 명시하고 반복 실행 결과를 검사한다. 숫자만 바꾼 재계산 문제가 아니라 변경 부작용을 다룬다.

연결: `notebook-execution-order`, `python-assignment-rebind`, `python-method-sort`, 기존 `py_kernel`·`py_methods`. 오답 수정 중 오류 출력이 남아 있다는 이유만으로 최종 통과를 막지 않는다.

### J3 `jupyter_restart`: 코드가 남는 것과 메모리가 남는 것을 구분하기

새 개념은 **재시작은 실행 상태를 새로 만드는 것이며 문서를 삭제하는 것이 아니다**이다. 출력 지우기, 커널 재시작, 실습 전체 초기화를 서로 다른 기능으로 설명한다.

소단계:

1. 변수와 계산이 있는 현재 상태에서 코드·설명 셀을 확인한다.
2. 같은 환경 커널을 실제 재시작한다. 새 커널에 과거 변수는 없고 코드 셀은 남는다.
3. 위에서 아래로 실행하여 문서만으로 결과가 다시 만들어지는지 확인한다.
4. 준비된 파일은 커널 메모리와 별개임을 파일 탭에서 확인한다. 앱 실습 초기화/VM 재생성과 커널 재시작을 혼동하지 않는다. 이 검사는 Colab 영구 저장을 증명하지 않는다.

- **예시 — 새 메모리에서 계산 다시 만들기:** C1 `price=12; count=4`, C2 `total=price*count`, 초기 커널에는 문서에 없는 `scratch=99`도 있음. 같은 환경을 재시작하고 두 셀을 재실행한다. 새 커널 세대, 코드/설명 유지, scratch 부재, total=48 확인. 단순 del/출력 지우기는 거부한다. scratch 삭제는 학습 목표인 ‘문서 밖 임시 값은 이어지지 않음’의 관찰이지 비밀 이름 암기 문제가 아니다.
- **활용1 — 남아 있던 변수에 의존하는 문서 수리:** 문서는 `total=price*count` 한 셀뿐이고 현재 메모리에는 price=9,count=3이 있어 우연히27이 나옴. ‘새 커널에서도27을 만들도록 필요한 입력 정의를 문서에 남기기’가 목표다. 재시작 후 위에서 아래로 재현되면 통과. 원래 출력27만 저장하거나 현재 세션에서만 정의하면 거부. 셀 합치기/분리는 자유다.
- **활용2 — 설명/파일과 메모리의 수명 구별:** 제공된 짧은 `source.txt`와 내용 확인용 준비 셀, Markdown 메모가 있음. 메모에 분석 목적을 남기고 같은 커널을 재시작한 뒤 준비 셀로 원본을 다시 읽고 `result`에 길이를 계산한다. 읽기 셀은 완성된 진단으로 제공하고 `open(...).read()` 의미만 설명한다. 통과: 실제 재시작, 메모/원본 유지, 새 실행으로 얻은 값. 이 문제에서는 파일을 작성·복사하거나 새로운 파일 API를 외우게 하지 않는다. 파일 삭제 후 문자열을 하드코딩해 결과만 맞추면 거부한다.

연결: `cloud-session-storage`의 메모리/파일 구분과 `notebook-execution-order`. 이 단원만 통과했다고 원격 세션 백업·복구 계획까지 완료 처리하지 않는다. 저장된 문서 출력과 현재 커널 결과는 화면에서도 구별해야 한다.

### J4 `jupyter_register`: 이미 있는 환경을 커널 목록에 등록하기

새 개념은 **환경 생성/패키지 설치/커널 목록 등록이 서로 다르다**는 것이다. 두 환경과 ipykernel은 이미 준비돼 있다. 개인 계정의 Jupyter 설정에 쓰지 않는다.

소단계:

1. 실제 Bash 탭에서 제공된 분석 환경을 활성화하고 `python -c "import sys; print(sys.executable)"`로 확인한다. 터미널 활성화가 이미 열린 노트북 커널을 자동 변경하지 않음을 설명한다.
2. 다음 형식을 설명한 뒤 문제의 실제 값이 채워진 명령을 제공한다: `python -m ipykernel install --prefix <실습전용등록경로> --name <고유등록이름> --display-name <화면이름>`. **이 prefix는 새 Python 환경을 만드는 위치가 아니라 커널 등록 파일의 설치 위치**다.
3. 목록을 새로고침하고 새 항목을 선택한다. name은 식별자, display-name은 화면 이름이며 같은 name으로 다시 등록하면 기존 등록이 대체될 수 있음을 미리 설명한다.
4. 실제 노트북 셀의 Python 경로로 등록 결과를 확인한다. 별도 jupyter CLI 암기는 필수로 요구하지 않는다.

- **예시 — 없는 분석 커널 등록:** A/B 환경은 있지만 A 등록만 있음. 제공된 `analysis-project`라는 새 이름으로 B를 등록·선택하여 `result=6*7`을 실행한다. 통과: 전용 등록 폴더의 유효한 kernelspec, 실제 B 프로세스와42. 이름만 있는 JSON·깨진 argv·다른 prefix면 거부한다.
- **활용1 — 그럴듯한 이름의 잘못된 등록 고치기:** 전용 `analysis-project`가 존재하지만 실제 argv는 A이고 display-name은 분석 Python임을 준비 설명에 밝힌다. B의 Python으로 같은 등록을 고치고 목록 새로고침·선택 후 NumPy 합을 실행한다. 실제 B와 계산값, A 등록 보존을 목표로 명시한다. display-name만 고치거나 B에 없는 임의 파일을 argv로 쓰면 거부. 정확한 CLI 문자열이 아닌 결과 상태로 판단한다.
- **활용2 — 기존 등록을 덮어쓰지 않고 별도 프로젝트 추가:** A/B 기본 등록이 이미 있음. **같은 B 환경**을 가리키는 새 `report-project` 등록을 추가하되 기존 두 항목을 그대로 사용할 수 있게 남긴다. 새 항목으로 문서를 실행하고 실제 B인지 확인한다. 새 Python 환경을 만들 필요는 없다. 기존 이름 재사용으로 하나를 덮어쓰면 거부한다. 표시 이름 문구는 학습자 자유이며 지정한 고유 식별자/실제 대상/보존만 검사한다.

동등한 결과를 만드는 허용된 등록 경로는 인정하되, 전용 등록 위치를 목표에 분명히 제시한다. app의 KernelSpecManager가 이 경로를 실제 검색하도록 준비해야 한다. 임의 prefix를 쓰면 자동으로 모든 프런트엔드 목록에 보인다고 설명하면 안 된다. 명령의 의미와 이름 덮어쓰기 규칙은 [IPython 공식 kernel 설치 안내](https://ipython.readthedocs.io/en/stable/install/kernel_install.html)를 확인했다. 새 shell 감시기나 명령 문자열 강제 채점은 제안하지 않는다.

### J5 `jupyter_package_target`: 설치된 곳과 실행하는 곳을 맞추기

새 개념은 **터미널에서 선택한 Python에 설치한 패키지가 다른 커널에 생기지는 않는다**는 것이다. pip의 install/import/Location은 기존 `pip_install`을 선행한다. 새 `freeze`, `-r`, shell 리다이렉션 또는 `%pip` 문법은 갑자기 요구하지 않는다.

소단계:

1. Bash의 `python -c "import sys; print(sys.executable)"`와 노트북의 sys.executable을 각각 보고 같은 환경인지 비교한다.
2. ‘이미 설치된 분석 환경을 선택’할 문제와 ‘지정된 기초 프로젝트 환경에 설치’할 문제의 목표 차이를 읽는다.
3. 설치가 필요할 때만 지정 환경의 `python -m pip install --no-index --find-links /opt/shellground/wheels numpy==2.3.5`를 사용한다. 공식 오프라인 wheel이 실제 준비된 경우에만 명령을 노출한다. 이는 이 연습의 고정 버전이지 최신 버전이라는 뜻이 아니다.
4. 해당 커널을 새로 시작하고 import·버전·`np.__file__`·작은 배열 계산을 확인한다. 설치는 현재 이름 공간에 `np`를 자동 정의하지 않는다. 재시작은 캐시가 남은 경우에도 새 상태로 검증하는 수단이며 모든 최초 설치 뒤 반드시 필요한 보편 법칙으로 가르치지 않는다.

- **예시 — 설치하지 않고 올바른 커널 선택:** Bash는 NumPy 있는 B, 노트북은 없는 A. 목표는 ‘기존 분석 환경을 사용하고 두 환경을 변경하지 않기’다. A의 ModuleNotFoundError를 관찰한 뒤 B를 선택하여 NumPy 계산을 한다. B 실제 prefix/import 경로/결과와 패키지 보존으로 판정. A에 설치해 오류를 없애거나 에러 문자를 출력해 진단을 흉내 내면 거부한다.
- **활용1 — 정해진 프로젝트에 필요한 패키지 준비:** 노트북 프로젝트는 A를 사용해야 하고 B의 기존 분석 작업은 보존한다. Bash는 B에서 시작. A를 선택해 공식 NumPy를 설치하고 A 커널에서 `[2,4,6]` 평균을 계산한다. 통과: A의 실제 NumPy2.3.5 설치·새 커널 import·mean=4, B 보존. B로 커널만 바꿔 계산하거나 B에 재설치하면 목표 미달이다. pip 제거/오설치 복구 자체는 기존17단원으로 안내한다.
- **활용2 — 두 환경 모두 import돼도 현재 위치 확인:** A/B 모두 실제 NumPy2.3.5가 준비된 별도 초기 상태다. ‘현재 노트북을 분석 환경 B로 실행하고 그 환경의 설치 위치를 확인, 패키지 변경 없음’이 목표다. 실제 B 커널의 버전/모듈 경로와 진단 답칸을 대조한다. 값이 같다는 이유로 A 출력이나 Bash의 결과를 노트북 결과로 제출하면 거부한다. 특정 stdout 서식·절대경로 철자 암기를 요구하지 않는다.

연결: `install-versus-import`, `package-roles`, `conda_interpreter`, `pip_install`. 관련 퀴즈 진도와 새 실습 완료는 분리한다. 실제 NumPy 경로/메타데이터 판정은 기존 공식 패키지 검증을 재사용하고 가짜 패키지 또는 명령 출력 모사는 만들지 않는다.

## 6. 구현 수용 기준과 남은 확인

- 5개 제안 단원/15문제 각각에서 초기 상태는 미완료여야 한다. 예시·활용1·활용2는 한 세션을 몰래 공유하지 않고 명시된 초기 상태를 제공한다.
- 소단계에서 설명한 이름과 실제 환경·파일·등록 경로가 일치해야 한다. 학습 화면에서 셀/터미널 입력 위치를 명시하고 Python 코드를 Bash 정답으로 오인시키지 않는다.
- 정상 참조와 동등 풀이 모두 실제 두 환경으로 확인해야 한다. 오답은 잘못된 prefix, 같은 버전 착각, 출력 지우기만 하기, 잔존 변수 의존, 반복 append, 이름만 고친 kernelspec, 등록 덮어쓰기, 다른 Python에 설치, 이전 출력 재사용을 포함한다.
- 커널 전환/재시작 시 코드·Markdown 유지, 변수 초기화, 늦은 이전 응답 분리, 실행 취소, 실패→같은 문서 수정→재채점을 확인한다. 실행 번호 자체를 고정 정답으로 삼지 않는다.
- 파일 유지 문제는 실제 앱의 보존 경계와 일치해야 한다. 커널 재시작만으로 로컬 파일이 없어지는 준비 방식은 수정해야 하며, VM 실습 초기화 뒤에도 파일을 보장한다고 확대 설명하지 않는다.
- 등록 CLI 문제는 실제 ipykernel과 지정 검색 경로가 먼저 준비돼 있어야 한다. 등록 실패/자산 부재/커널 기동 실패를 학습자 계산 오답과 분리한다.
- 5단원마다 복습을 두는 기존 규칙을 이 새 분야에도 적용한다면, 위5개 뒤에 별도 복습을 후속 설계한다. 이번15문제의 J5를 ‘직전5개 복습’이라고 표시하면 자기 자신을 포함하게 되므로 그렇게 부르지 않는다.
- 이 보고서는 **설계만 완료**했다. 실제 노트북 수업 연결, 15문제 참조/미완료/오답/동등풀이 검증, Linux 실행 가능한 검토판 인수는 부모 구현의 다음 게이트다. Windows→Android→macOS 순서는 사용자 최신 승인대로 그 뒤에 진행하며 이 보고서가 포팅 완료 증거는 아니다.

추가 큰 API 누락을 단정하지 않는다. 우선 실제 Jupyter 행동, 병렬성의 짧은 개념 확인, 날짜 인덱스와 mean/count 결합의 좁은 평가를 닫고, 위 낮은 우선순위 API 표기를 ‘강의에 등장한 표기까지 모두 직접 실행’이라는 완료 기준에 포함할지 명확히 결정하는 것이 적절하다.
