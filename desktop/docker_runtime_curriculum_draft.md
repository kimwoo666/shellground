# Docker 21–25 후속 과정 초안

2026-09-18 · 설계만 작성. 과정 등록·채점 구현·VM 실행·성능 검증은 하지 않았다. 기존 16–20 및 시뮬레이터는 변경하지 않는다.

## 공통 계약

- 대상은 앱 전용 Linux guest의 실제 Docker daemon뿐이다. 아래의 ‘호스트’는 그 guest이며 개인 PC의 포트·장치·Docker socket·X 서버에 접근하지 않는다.
- 선수: 이미지/컨테이너 수명, inspect, bind/volume, UID/GID, 셸 인자·인용·분기·종료 상태, 기존 Docker 16–20. 새 옵션은 사용 직전 한 가지 역할씩 설명한다.
- 준비물: 오프라인 실제 이미지, 제공된 조회 도구, 충돌 없는 전용 이름/포트, 보호 파일·컨테이너·볼륨·네트워크. HTTP 이미지에는 실제 서버가 있어야 하며 기존 Alpine에 서버가 있다고 가정하지 않는다.
- 부하는 `sleep 120` 중심, HTTP는 소수 요청, stats는 1–3회 표본만 사용한다. busy loop·대용량 dd·fio·GPU 계산·반복 성능 측정은 요구하지 않는다. 수명 만료는 정답 오류가 아니라 환경 만료로 안내한다.
- 목표에 보존 대상과 삭제/재생성 허용 대상을 명시한다. 종료한 컨테이너도 검사 전에는 남겨 설정을 확인한다. 파일 내용만 맞거나 이름만 같은 객체로 바꾼 것은 실행·보존의 증거가 아니다.
- 상태는 ‘개념 확인 / 실제 조사 완료 / 설정 적용 확인 / 기능 실행 확인 / 지원 조건 미충족 / 미실행’을 구별한다. 지원 조건 미충족을 기능 성공으로 올리지 않으며 전체 완료 화면에도 미실행 범위를 남긴다.
- 고정 CPU%, 메모리 사용량, MB/s, GPU 점수는 정답이 아니다. 변경될 수 있는 값은 같은 시점의 실제 관측 자료로 판단하고, 이후 재조회와 문자열 일치를 강요하지 않는다.
- 내부 안전 조건(작업 시간/메모리/프로세스 상한·개인 호스트 격리)은 문제 목표와 구분한다. CLI 문자열·옵션 순서가 아니라 실제 객체·권한·설정·응답으로 동등 풀이를 인정한다.

## 21. 공개 포트와 실제 HTTP 응답 — 가칭 `docker_runtime_http`

설명: 포트 매핑은 서버 프로세스나 정상 응답을 대신하지 않는다. guest의 `127.0.0.1:PORT`와 컨테이너 내부 서버 포트를 구별한다. 주소를 생략한 공개는 범위가 넓다. [Docker 공개 포트](https://docs.docker.com/engine/network/port-publishing/)

1. 준비된 서버의 내부 포트·문서 루트·기대 경로를 읽고, host/container 포트 순서를 짧은 예로 구분한다.
2. `-p 127.0.0.1:지정포트:서버포트`로 시작한 뒤 inspect/port로 실제 연결을 읽는다. 생성 전 inspect를 먼저 요구하지 않는다.
3. 제공된 HTTP 클라이언트의 조회/헤더/시간 제한 옵션을 설명한 후 guest loopback에 직접 요청한다. 연결 실패, HTTP 오류, 정상 본문은 다른 결과다.
4. 허용된 파일 또는 실행 설정만 고쳐 다시 요청하고, 보호 자료와 공개 범위를 함께 확인한다.

- 예시: 준비된 문서를 읽기 전용으로 연결한 서버를 loopback에 공개하여 `/health.txt`의 현재 내용과 HTTP 200을 받는다. 원본 내용과 서비스 컨테이너를 보존한다.
- 활용1: 포트는 맞지만 문서 루트에 필요한 파일이 빠져 실제 404인 서비스를 준비한다. 제공된 원본에서 지정 목적 파일만 복구하고 같은 컨테이너 ID로 200을 받는다. 포트 변경·컨테이너 교체는 불필요하다.
- 활용2: 전용 격리 guest 안의 잘못된 공개 주소를 loopback으로 좁힌다. 대상 컨테이너만 재생성하도록 명시하고 문서·데이터 볼륨과 다른 서비스를 보존한다. 내부 서버 포트는 유지한다.
- 채점: 실제 image ID, Running, HostIp/HostPort/내부 포트, mount와 읽기 전용 원본을 검사하고 별도 실제 HTTP GET으로 상태·본문을 확인한다. 보고서만 작성, 엉뚱한 서비스 응답, 모든 주소 공개, 보호 데이터 손상은 거부한다.
- 준비 게이트: 실제 서버/클라이언트·포트·guest 격리 확인이 실패하면 실행 미준비다. 공식 문서의 구버전 localhost 공개 주의 때문에 Docker 28 미만을 무조건 외부 차단이라고 설명하지 않는다. 개인 네트워크에서 접근 시험하지 않는다.

## 22. 순간 사용량과 설정 한도 — 가칭 `docker_runtime_stats`

설명: `stats`는 관측값이며 예약량·성능 점수가 아니다. `MEM USAGE / LIMIT`의 두 값을 분리하고 CPU 한도는 inspect에서 따로 읽는다. Linux CLI 메모리 표시와 원시 API 값은 캐시 처리 때문에 다를 수 있다. [Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/)

1. 짧게 대기하는 실제 컨테이너를 대상으로 `docker stats --no-stream 이름`을 읽고 이름/사용량/한도를 구분한다.
2. 기존 inspect로 메모리 한도와 CPU 설정을 확인한다. 단위 변환은 제공 예로 설명하며 0.00%를 제한 미적용으로 판단하지 않는다.
3. 현재 사용량이 아닌 한도로 요구사항을 판단하는 두 컨테이너 사례를 비교한다. `PIDS`는 프로세스만의 개수라고 가르치지 않는다.
4. 정지된 컨테이너의 상태를 inspect와 함께 읽고, 실시간 자료가 없거나 0 표시인 경우를 ‘메모리 한도 0’으로 쓰지 않는다.

- 예시: 메모리 한도가 있는 실제 대기 컨테이너에서 사용량 열과 한도 열을 올바르게 구분해 기록한다. 낮은 CPU 사용량만으로 한도 실패를 선언하지 않는다.
- 활용1: 서로 다른 한도를 가진 두 준비 컨테이너 중 ‘지정 메모리 한도 이하’ 조건을 충족하는 대상을 고른다. 우연히 지금 덜 쓰는 대상을 고르는 문제와 구별한다. 객체 설정은 바꾸지 않는다.
- 활용2: 정지된 컨테이너를 ‘0B 한도’라고 쓴 이전 보고서를 고친다. 정지 상태·설정 한도·현재 사용량 미관측을 나누고 재시작하지 않는다.
- 채점: 실제 ID/상태/한도와 답의 대상·열 의미를 비교한다. 순간값의 출처가 필요한 문제는 앱이 실제 Docker API에서 시각·ID와 함께 수집한 읽기 전용 관측 표본을 제공한다. 학습자가 별도로 실행한 stats 숫자와 그 표본의 완전 일치를 요구하지 않는다.
- 거부/경계: 사용량을 한도로 보고, 정지 자료를 실시간 성능으로 보고, 다른 ID의 자료를 사용하면 오답이다. 단위·표현이 동등한 답은 허용한다. 통계 수집 실패는 관측 미확인이지 0 사용으로 만든 성공이 아니다.

## 23. CPU 시간 상한과 실행 CPU 집합 — 가칭 `docker_runtime_cpu`

설명: `--cpus`는 CPU 시간 상한, `--cpuset-cpus`는 실행을 허용할 CPU 번호 집합이다. 특정 CPU 독점이나 항상 그만큼 쓰겠다는 약속이 아니다. [Docker 자원 제한](https://docs.docker.com/engine/containers/resource_constraints/#cpu)

1. guest에서 실제 허용된 CPU 목록을 먼저 보여 준다. 0–3을 고정 가정하지 않고, 문제에 사용할 CPU 하나/집합을 명시한다.
2. `--cpus=0.5`로 대기 컨테이너를 만들고 inspect와 실제 cgroup의 quota/period를 읽는다. 두 수의 비율로 상한을 해석한다.
3. `--cpuset-cpus`를 별도로 적용해 요청 목록과 실제 유효 목록을 비교한다. `0,1`과 `0-1`처럼 같은 집합을 나타내는 표기를 인정한다.
4. 두 조건을 조합해 오설정을 고친다. cgroup v2의 `cpu.max`, `cpuset.cpus.effective`는 읽기만 하며 부모 제한도 따로 설명한다. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

- 예시: CPU 번호를 고정하지 않고 CPU 시간 상한만 0.5로 제한한 대기 컨테이너를 만든다. 실제로 50%를 소비시키는 목표는 없다.
- 활용1: 지정된 허용 CPU 부분집합에서만 실행하도록 만들고 이 컨테이너 자체의 CPU quota는 추가하지 않는다. 상위 환경에 제한이 없다는 뜻으로 확대하지 않는다.
- 활용2: ‘CPU 하나 분량 제한’을 ‘CPU 번호 하나 선택’으로 잘못 작성한 시작 초안을 고친다. 명시된 시간 상한과 CPU 집합을 동시에 만족시키며 원래 입력 자료는 보존한다.
- 채점: 실제 컨테이너 PID와 그 cgroup을 연결하여 quota 비율·effective CPU 집합·inspect 설정을 대조한다. NanoCpus 값 하나만 강제하지 않고 동등한 quota/period 설정도 허용한다. 부모 제한으로 숫자가 줄어든 경우에는 원인을 구분한다.
- 준비 게이트: 앱이 실제 cgroup 버전·경로·사용 가능한 controller를 먼저 찾고 조회 경로를 제공한다. v1은 대응 파일을 검증한 분기만 지원한다. 파일을 못 찾으면 적용 미확인이다. 지원 부족을 해결하려고 호스트 재부팅·controller 쓰기를 요구하지 않는다. [Docker 실제 cgroup 조사](https://docs.docker.com/engine/containers/runmetrics/)

## 24. 블록 I/O 가중치의 적용 조건 — 가칭 `docker_runtime_io_weight`

설명: `--blkio-weight`는 상대 가중치이지 고정 MB/s나 두 배 속도 보장이 아니다. Docker 문서의 direct I/O 주의와 실제 controller/저장장치 조건을 함께 읽는다. [Docker blkio](https://docs.docker.com/engine/containers/run/#block-io-bandwidth-blkio-constraint)

1. 블록 장치 I/O, 메모리 캐시, 상대 가중치와 속도 상한의 차이를 설명한다. `stats`의 BLOCK I/O 누적량을 MB/s로 부르지 않는다.
2. 앱이 guest의 Docker 경고·cgroup 버전·I/O controller·실제 가중치 인터페이스·대상 가상 저장장치 지원을 읽기 전용으로 조사해 자료를 제공한다.
3. 지원이 확인된 경우에만 작은 대기 컨테이너에 가중치를 요청하고 inspect와 실제 제어 파일을 비교한다. v1/v2의 수치 범위를 같다고 가정하거나 요청값을 제어 파일 값으로 복사하지 않는다.
4. ‘요청됨 / 실제 적용 확인 / 성능 효과 미측정’을 별도 칸으로 기록한다. 지원 경고 또는 적용 파일 부재는 미확인으로 남긴다. [Linux blkio](https://docs.kernel.org/admin-guide/cgroup-v1/blkio-controller.html), [Linux BFQ](https://docs.kernel.org/block/bfq-iosched.html)

- 예시: 가중치 300 요청을 시도하되 실제 지원 여부와 적용 결과를 구분해 보고한다. 지원되면 설정 적용까지, 안 되면 정확한 지원 조건 조사까지만 완료한다.
- 활용1: 같은 제어 대상의 두 대기 컨테이너에 서로 다른 가중치를 구성하고 순서·대상을 실제 설정으로 확인한다. 경쟁 I/O를 발생시키거나 속도 비율을 맞추지 않는다.
- 활용2: ‘설정 600이므로 600MB/s 보장’이라는 오래된 보고를 실제 요청/적용 관측으로 고친다. 현재 컨테이너와 장치 설정은 바꾸지 않고 성능 미측정을 명시한다.
- 채점: 실제 Docker 설정·경고·활성 제어 인터페이스와 답의 구분을 대조한다. 런타임의 가중치 변환을 확인한 구현만 적용 판정을 한다. 상대 순서만 맞아도 요청값이 틀리면 거부한다. 지원되지 않을 때 적용 문제를 자동 PASS시키지 않는다.
- 범위 제한: 이 묶음은 I/O 성능 검증이 아니다. 고정 처리량·속도 비율·효과 없음이라는 단정 모두 증거 없이는 거부한다. 직접 장치 쓰기, scheduler 변경, 개인 디스크 연결은 하지 않는다.

## 25. 최소 권한 시작 스크립트와 장비 조건 — 가칭 `docker_runtime_safe_launcher`

설명: 필요한 작업과 권한을 먼저 정한다. UID, capability, 파일 쓰기 위치는 다른 제한이다. 장치·GPU·화면 준비 판단은 기존 개념 카드를 재사용하고 실제 성공 범위를 분리한다. [Docker 실행 보안 옵션](https://docs.docker.com/reference/cli/docker/container/run/), [Docker GPU 준비](https://docs.docker.com/engine/containers/gpu/)

1. 이미 배운 UID/GID·읽기 전용 입력·쓰기 출력·인자 인용으로 한 파일 처리 스크립트를 읽는다. 이 작업은 장치와 네트워크가 필요 없다고 명시한다.
2. 새 옵션 `--cap-drop=ALL`, `--read-only`, `--security-opt=no-new-privileges`를 각각 설명하고 짧은 실행을 따로 확인한다. 처음부터 세 옵션과 새 셸 문법을 한 줄에 몰아 시험하지 않는다.
3. 제한을 결합한 시작 스크립트를 직접 실행하고 실제 UID/GID·권한·입출력·종료 상태를 확인한다. 검사용 컨테이너를 남기며 root 실행 후 chown만 한 결과는 충분하지 않다.
4. 현재 guest의 장치 노출·드라이버/런타임 준비·전용 화면 지원 관측을 기존 카드와 대조한다. 확인하지 않은 기능은 미확인이다. `--privileged`, 개인 GPU 전달, Docker socket·개인 X 소켓 공유, `xhost +`를 해결책으로 실행하지 않는다.

- 예시: 준비된 안전한 파일 처리 계약을 만족하는 비root 시작 스크립트를 완성한다. capability 제거·권한 상승 금지·읽기 전용 rootfs·지정 출력만 쓰기 가능을 실제 설정으로 확인한다.
- 활용1: 불필요하게 권한을 넓힌 스크립트 초안을 실행하기 전에 고친다. 새 공백 포함 입력 경로에서도 결과가 같고, 입력 부재 때는 명시된 비성공 종료와 기존 출력 보존을 확인한다. 위험한 원본 초안은 자동 실행하지 않는다.
- 활용2: guest에서 현재 관측 가능한 준비 조건을 인계 보고로 작성하고, 준비된 CPU 파일 처리만 제한된 스크립트로 실제 실행한다. device 접근·GPU 계산·X11 표시는 각각 미지원/미확인/미실행을 구별하며 CPU 성공으로 대체 완료하지 않는다.
- 채점: 앱 전용 경로의 스크립트를 learner 권한으로 제한 시간 안에 실행하여 새 컨테이너 ID·이미지·Config.User·HostConfig·실제 UID/GID·출력·입력 보존을 검사한다. 옵션 문자열 일치가 아니라 의미가 같은 실제 제한을 인정한다. AppArmor/seccomp 해제·추가 장치/권한은 허용된 계약 밖이다.
- 미지원 처리: 장비 기능의 실제 실행 평가는 이 묶음에서 하지 않는다. GPU 이미지/환경변수/장치 이름의 존재만으로 GPU 성공, DISPLAY 값만으로 X11 성공을 표시하지 않는다. X11 판단 근거는 이미 검토된 기존 카드의 공식 출처를 그대로 표시한다.

## 구현 전 승인·검증 조건

- 각 단원은 예시→활용1→활용2의 준비·정답·미완료·대표 오답·동등 풀이만 증분 검증한다. 기존 전체 과정을 반복하지 않는다.
- 5단원 복습은 이미 배운 HTTP 요청 1회·한도/관측 구분·CPU 설정 확인·I/O 지원 판정·안전 스크립트를 조합하되, 장비 미실행을 별도 표시한다. 새 API나 벤치마크는 추가하지 않는다.
- Linux 검토판에서 실제 지원/미지원 분기와 오답 거부를 먼저 확인한다. 이 문서나 개념 정답만으로 실행 기능·다른 OS 지원·포팅 완료를 주장하지 않는다.
