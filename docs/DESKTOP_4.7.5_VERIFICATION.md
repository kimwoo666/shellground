# Desktop 4.7.5: 미리 준비하는 실습 환경

Windows와 Linux에 같은 시작 정책을 적용한다. 실제 앱을 열면 모드 선택 화면 뒤에서 전용 VM과 Docker를 준비하고, Linux 학습 화면이 그 VM을 그대로 인계받는다. ROS 노드와 문제별 자료는 실습을 선택했을 때 준비한다.

설명 화면이나 다음 단원으로 이동할 때 이전 터미널·학습자 프로세스·문제 파일은 정리하지만 VM은 유지한다. Python 또는 시뮬레이션을 선택하면 불필요해진 미리 부팅 작업을 취소한다. 모드 선택창을 닫거나 학습 앱을 종료하면 미리 부팅 중인 VM도 정리한다. 저장된 학습 진도와 메모의 경로·형식은 변경하지 않는다.

속도 우선 정책이다. VM의 게스트 RAM 설정은 2 GiB로 유지하며, Windows/Linux의 실제 상주 메모리나 CPU 절감 수치를 주장하지 않는다. Windows WHPX CPU 예산 개선은 [이전 시작 속도 검증](WINDOWS_STARTUP_VERIFICATION.md)을 참고한다.

## 수정 소스에서 확인한 결과

Windows WHPX에서 기존 설치 런타임과 동일한 기본 디스크를 사용했다. 전체 과정을 다시 채점하지 않고 이번에 변경한 시작·단원 이동·종료를 검사했다.

| 항목 | 관찰값 |
| --- | ---: |
| 백그라운드 준비 요청이 돌아오는 시간 | 0.001초 |
| 백그라운드 Linux·Docker 준비 완료 | 8.759초 |
| 준비 완료 후 첫 실습에서 실제 터미널 출력까지 | 0.437초 |
| 설명 복귀 후 다음 실습에서 실제 터미널 출력까지 | 0.329초 |

두 실습에서 같은 VM 프로세스와 임시 디스크가 유지됐다. 종료 후 VM·부팅 스레드 종료와 임시 디스크 제거를 확인했다. 이는 해당 PC의 수정 소스 측정이며 모든 장치의 속도를 보장하는 수치가 아니다.

로컬 회귀 검사 53개 통과. 배포 CI는 Windows와 Linux에서 시작/취소·UI·진도 보존 검사, 새 실행 파일의 리소스·worker·UI 검사를 수행한다. Linux에서는 실제 supervisor 수명 검사와 설치 프로그램의 이전 디스크 재사용도 검사한다. 두 빌드가 성공한 뒤에만 같은 릴리스에 게시한다.

## 설치와 기존 자료

Windows와 Linux 설치파일은 같은 `v4.7.5` 릴리스에 배포한다. Linux의 기존 4.7.4 설치가 있으면 SHA-256이 같은 기본 디스크를 하드 링크로 재사용한다. 기존 학습 기록은 앱 설치 폴더와 별도의 사용자 데이터 폴더에 그대로 남는다.

Linux GUI·프로세스 검사는 CI 환경의 증거이며, 사용자의 Linux PC에서 직접 실습 VM을 다시 실행한 증거는 아니다.
