# Windows 터미널 시작 속도 개선

대상: `4.7.4-windows.3`. Windows 11 x64, 논리 CPU 12개, WHPX 하드웨어 가속에서 측정했다. Windows 가속이 없는 PC의 성능을 보장하는 수치는 아니다.

## 변경과 측정

기존 Windows supervisor는 WHPX에도 TCG와 같은 0.6코어 합계 제한을 적용했다. 이제 WHPX는 호스트 논리 코어 절반, 최대 4코어분을 사용한다. 낮은 프로세스 우선순위, CPU hard cap, 앱 종료 시 VM을 함께 종료하는 Job Object는 유지한다. TCG 소프트웨어 실행 제한은 0.6코어로 유지한다.

부팅 뒤 14개 채점 파일을 각각 Python 프로세스로 전송하던 방식은 한 번의 전송으로 바꿨다. 소유한 게스트인지 확인하고, 허용한 파일 이름과 모든 Python 소스를 검사한 다음 게스트의 임시 실습 디스크에 설치한다.

동일한 설치 런타임과 기본 디스크를 사용한 소스 실행 비교다. 시작 버튼 이후에 수행되는 `RealEngine.boot()` 시작부터 Bash에서 확인용 명령의 실제 출력이 도착할 때까지 측정했다. 앱 첫 창을 여는 시간이나 다운로드 시간은 포함하지 않는다.

| 측정 | 변경 전 | 변경 후 1회 | 변경 후 2회 |
| --- | ---: | ---: | ---: |
| 게스트 연결 후 셸 설정 시작 | 23.279초 | 5.538초 | 5.717초 |
| 채점 파일 설치 | 11.208초 | 0.299초 | 0.467초 |
| 터미널 명령 실행 가능 | 36.994초 | 6.922초 | 7.048초 |
| 종료 | 2.405초 | 2.110초 | 2.116초 |

약 81% 단축을 관찰했다. 모든 측정에서 VM 종료와 임시 세션 삭제가 확인됐다. 기본 실습 디스크는 공유하며 새 사본을 만들지 않았다.

캐시가 준비된 상태에서 이전 소스 커밋을 다시 실행한 대조 측정도 35.870초였다(채점 파일 설치 10.092초). 새 버전의 7초 결과를 단순한 첫 실행 캐시 차이로 설명할 수 없었다.

## 검사 범위

- Windows CPU 예산과 Job 설정, 가속 종류 선택, 부팅 경로, 파이프, ROS 준비 상태, 채점 전송 및 오류 처리: 소스 회귀 검사 48개 통과.
- 채점 파일에 잘못된 이름 또는 문법 오류가 있으면 파일 쓰기를 시작하기 전에 실패하는지 확인했다.
- 실제 Linux·ROS 2·게스트 화면·APT·계정/권한·Docker 갱신/보관/복원/배포 진단 통과. 부팅 6.18초, 전체 검사 51.58초, 종료 2.16초.
- [Windows 배포 작업](https://github.com/kimwoo666/shellground/actions/runs/35436597110) 성공. 배포 커밋 `c94835aec8d1b6e07688f23bf4124b09082925a6`. CI에서 frozen 파이프/Job, 리소스와 scientific worker, 학습 UI·키보드·worker 종료 검사 통과.
- 게시된 설치파일을 Windows에서 실행해 설치 성공(exit 0), SHA-256과 설치 영수증 확인. 기존 바탕화면 아이콘이 `4.7.4-windows.3`을 가리키는 것도 확인했다. 기존 7.8GB 기본 디스크를 하드 링크로 재사용했다.
- 설치된 배포 EXE의 추가 실습·강제 종료 검사는 사용자 요청으로 생략했다. 위 7초 수치는 동일 수정 소스와 설치 런타임을 이용한 측정이며, 배포 EXE를 다시 측정한 결과가 아니다.
